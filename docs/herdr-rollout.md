# herdr rollout checklist

Working document for adding [herdr](https://herdr.dev) to the terminal stack. Delete
it once the work lands and the rationale has moved into `docs/decisions.md`.

## Status

Checklist A shipped on 2026-09-04, on branch `feat/herdr`. Two items in it stayed
open on purpose and are the first things to pick up:

* **Shell completions are not installed.** `herdr completion <shell>` works, but
  wiring it into `~/.zshrc` or `$PROFILE` costs a subprocess on every shell start.
  It needs a cached, version-keyed script before it ships.
* **Tab titles are not herdr-aware.** `_ts_tab_title` / `Set-TsTabTitle` call
  `wezterm cli set-tab-title`, which does nothing inside a herdr pane. herdr has a
  `--label` on its pane commands and exports `HERDR_PANE_ID`, so the branch is
  detectable; it is simply not written.

Three things below were written before the binary was installed and turned out to
be wrong on contact with a real machine. They are corrected in place, and noted
here because the reasoning matters more than the fact:

* **The managed config is a key SPLICE, not a whole-file render.** The Ghostty
  pattern was the right model for ownership, backups and a local-only `off`, but
  not for the write itself: herdr rewrites `config.toml` and so does the user, and
  the first machine already had hand-written settings in it.
* **`themeMode`, not `resolvedTheme`, was the wrong question entirely.** herdr has
  an OS-following mode (`theme.auto_switch`), which this document said it did not.
  The answer used neither: `theme.name = "terminal"` follows the terminal's own
  palette, so one value is right in all three modes and the stack never becomes a
  second theme owner.
* **There is no `current` junction on Windows.** The installer unpacks to
  `%USERPROFILE%\.herdr\packages\standalone\releases\<version>-<triple>\` and
  puts that on the user PATH.

Checklists B through F are untouched: they are the per-OS install runs, and only
Windows has been through one.

## What herdr is

A terminal multiplexer written as one Rust binary, aimed at hosting AI coding
agents. It runs a background server; panes survive detach, network loss and
reboot. Every pane is marked working, blocked or idle. Agents drive it through a
CLI and a local socket API. It does not wrap Claude Code, Codex, Cursor or Grok;
it owns their terminals. Apache-2.0, publisher "Herdr, Inc.".

Facts established on 2026-09-04, all of which the checklists below depend on.
Re-verify anything marked here before shipping, because 0.8.x is moving fast.

| Fact | Value |
|---|---|
| Current version | 0.8.2 stable, with a preview channel published alongside |
| Config path, POSIX | `~/.config/herdr/config.toml` |
| Config path, Windows | `%APPDATA%\herdr\config.toml`; `HERDR_CONFIG_PATH` overrides |
| Config format | TOML, generated by `herdr --default-config` |
| Config reload | `herdr server reload-config`; startup-only settings still need a restart |
| Default prefix | `ctrl+b` |
| Built-in themes | `catppuccin` (default), `terminal`, `tokyo-night`, `dracula`, `nord`, `gruvbox`, `one-dark`, `solarized`, `kanagawa`, `rose-pine`, `vesper`; plus `theme.auto_switch` with `dark_name`/`light_name` |
| Completions | `herdr completion <zsh, bash, fish, powershell, elvish>` |
| Channel | `herdr channel show` and `herdr channel set stable preview`, direct installs only |
| Self-update | `herdr update` |
| Env vars exported into panes | `HERDR_SOCKET_PATH`, `HERDR_SESSION`, `HERDR_PANE_ID`, `HERDR_TAB_ID`, `HERDR_WORKSPACE_ID` |

Install routes:

| Platform | Command |
|---|---|
| Linux, macOS, WSL | `curl -fsSL https://herdr.dev/install.sh \| sh` |
| macOS, alternative | `brew install herdr` |
| Windows | `powershell -ExecutionPolicy Bypass -c "irm https://herdr.dev/install.ps1 \| iex"` |
| Windows, endpoint-protected | `curl.exe -fsSLo install.cmd https://herdr.dev/install.cmd && install.cmd && del install.cmd` |
| Any, version manager | `mise use -g herdr` |
| Nix | `nix run github:herdrdev/herdr/v0.x.y` |
| Manual | binaries at https://github.com/herdrdev/herdr/releases |

## Decisions settled on 2026-09-04

These are answered. Everything below follows from them; if one is revisited, the
checklist items it drives are named in each entry.

1. **herdr sits beside tmux.** tmux stays the `ssht` persistence story on servers,
   herdr is opt-in, and the stack never starts it automatically. Nothing existing
   changes; the cost accepted is that a machine can have three multiplexers
   available at once.
2. **herdr keeps its own default prefix, `ctrl+b`, and gets no saved setting.**
   Matching upstream means every herdr tutorial and doc applies unmodified, and
   there is one fewer key in the store.
   **Known collision, deliberately accepted:** `ctrl+b` is also this stack's
   `tmuxPrefix` default, so tmux running inside a herdr pane is unreachable until
   one of the two is rebound by hand. Because herdr sits beside tmux rather than
   replacing it (decision 1), that nesting is a reachable state. The mitigation is
   a `tstack doctor` warning, not a new setting: doctor reports the collision and
   names the two places to change it (`tstack config` for `tmuxPrefix`, herdr's own
   `config.toml` for its prefix). Revisit this if the warning starts firing on
   every machine.
3. **The config file is managed, on the Ghostty pattern.** One Python
   implementation, opt-in through `herdrConfig`, a backup before the first write,
   and `off` restores that backup on that machine only. Never a `.chezmoiremove`
   and never a sync-side delete, because both run everywhere and would wipe a
   hand-written config on a box that never opted in.
4. **The release channel is detected, never stored.** Read it back with
   `herdr channel show`, exactly as the WezTerm channel is read from winget rather
   than persisted. A stored value can disagree with reality; a read-back cannot.
5. **`tstack update` reports a newer herdr and does not install it.** Updating a
   live multiplexer is the same hazard class as restarting the WezTerm mux server,
   which this stack deliberately never automates. Print the version gap and the
   `herdr update` command.
6. **On a combined Windows plus WSL machine, both sides run their own server.**
   Two independent installs, two sockets, no stack opinion about which one you
   attach to. The consequence to build for: `tstack herdr status` has to report
   both, clearly labelled, rather than assuming one authoritative server. Neither
   side may set `HERDR_SOCKET_PATH` for the other.

## Checklist A: shared work, done once

Ordered so that each step is verifiable before the next one starts.

- [x] Add one row to `bootstrap/apps.conf`:

- [x] Add an explicit id-list route instead, mirroring the `$TsPyTools` and
      `Test-TsAppIsPy` precedent: `ts_app_is_herdr` in `bootstrap/_config.sh` and

- [x] Write the installers: `ts_install_herdr` in bash and `Install-TsHerdr` in
      pwsh. Both must be idempotent, skipping when the binary is already on PATH,

### The managed config

- [x] Map `resolvedTheme` to a herdr theme name. Read `themeMode` instead only if

- [x] `off` removes the managed file on that machine only. Never add it to

- [x] Verify whether herdr's TOML parser accepts the comments we would write, with

## Checklist B: Windows

Run this one first. `tstack` is driven from pwsh on this machine, so the pwsh
entry path is the one that must work.

### Install

- [ ] Do **not** use winget. There is no stable `Herdr.Herdr` manifest; only
      `Herdr.Herdr.Preview` is published by Herdr, Inc. The other three hits
      (`hdosys.herdr-win`, `khanhtd36.herdr-khanhtd36`, `hdosys.herdr-sandbox`)
      are third-party republishes and must not be used. Re-check before shipping
      with `winget show --id Herdr.Herdr --exact`.
- [ ] Have `Install-TsHerdr` run the official installer:
      `powershell -NoProfile -Command "irm https://herdr.dev/install.ps1 | iex"`.
      Run it under Windows PowerShell rather than pwsh, matching the `claude`,
      `grok` and `cursor-agent` branches. Execution policy is not a concern: it
      governs script files, and `iex` on a string is unaffected.
- [ ] Add the `install.cmd` fallback for endpoint-protected machines:
      `curl.exe -fsSLo install.cmd https://herdr.dev/install.cmd && install.cmd && del install.cmd`.
      Print it in the warning path rather than running it silently.
- [ ] Call `Update-TsSessionPath` after the install, so the rest of the bootstrap
      run can see the new binary. The installer uses a versioned install folder
      plus a `current` junction, so the PATH entry is stable across updates.
- [ ] Confirm the guard: `Install-TsHerdr` must skip when `herdr` is already
      resolvable as an Application command, the same way the agent CLI installers
      do.
- [ ] Record in the docs that Windows ARM64 runs the x86_64 binary under
      emulation.

### Verify the install by hand, once

- [ ] `herdr --help`, and confirm the resolved config path it prints is

- [ ] `herdr channel show`
- [ ] `herdr status`
- [ ] Check whether Defender or SmartScreen interfered with the unsigned binary,

### Config file

- [ ] `%APPDATA%\herdr\config.toml` resolves to
      `C:\Users\<you>\AppData\Roaming\herdr\config.toml`, which is under the
      Windows home. If the config is templated through the mirror rather than
      written by `tstack/herdr.py`, the source path is
      `windows/AppData/Roaming/herdr/config.toml.tmpl` and the existing
      relative-path-preserving sync needs no script change. There is a precedent

- [ ] If it is templated, use `__WIN_USER__` and the existing `__TS_*__` token
      style for the theme. There is no prefix token: decision 2 leaves the prefix
      at herdr's own default. Never Go-template syntax under `windows/`.
- [ ] Confirm the token substitution list in `scripts/sync-windows.ps1` and in
      `run_after_90-sync-windows.sh` both cover any new token. A token added to
      only one of them produces a machine that renders correctly under one sync
      path and literally under the other.
- [ ] Take a `.bak.YYYYMMDD` of any pre-existing config before the first write.

### pwsh integration

- [ ] Add the `herdr` marker block to
      `windows/Documents/PowerShell/Microsoft.PowerShell_profile.ps1`. Edit the
      repo source inside a marker block; anything hand-added to the live
      `$PROFILE` is replaced on the next sync.
- [ ] Register completions with `herdr completion powershell`. Guard the
      registration with `Get-Command herdr -ErrorAction SilentlyContinue` so a
      machine without herdr does not throw on every shell start.
- [ ] Keep `local-overrides` last in the profile.
- [ ] Personal herdr tweaks go in `profile.local.ps1`, never in `$PROFILE`.

### Windows traps to check explicitly

- [ ] No pwsh local may share a parameter's name in any casing. An AST scan test
      exists, `test_no_pwsh_local_shadows_a_typed_parameter`; make sure the new
      pwsh functions pass it.
- [ ] Never pipe `Where-Object` straight into `Set-Content`. An empty pipeline
      leaves the file untouched with no error.
- [ ] Verify the new files are LF in the working tree. `.gitattributes` handles
      this, but confirm rather than assume.
- [ ] Test the entry path from pwsh first: `tstack herdr status`,
      `tstack config herdr on`, `tstack config herdr off`. Never pipeline-capture
      `& pwsh` output when testing.
- [ ] On a combined Windows plus WSL machine, remember the WSL apply is
      authoritative and its sync writes the Windows `config.json` mirror. A
      pwsh-side save followed by a WSL apply loses the pwsh-side value. Save from
      WSL, or verify the value survives both.
- [ ] Test over ssh as well as at the console. The Windows box listens on 2222,
      and a remote-token session breaks things a console session never shows,
      especially anything that assumes an interactive `irm | iex`.
- [ ] Check herdr running inside WezTerm on Windows, both with `weztermMux off`
      and with it `on`. With the mux on, panes are hosted by
      `wezterm-mux-server`, which is a Windows process reached through interop,
      never `pgrep`.
- [ ] Reproduce the decision 2 collision on purpose: start tmux inside a herdr
      pane, confirm `ctrl+b` reaches herdr and not tmux, and confirm
      `tstack doctor` warns about it. That warning is the whole mitigation, so it
      has to actually fire.
- [ ] Per decision 6, confirm the Windows server and the WSL server coexist: both
      running, both listed by `tstack herdr status`, and attaching to one does not
      disturb the other.

### Windows verification

- [ ] `tstack doctor` clean apart from the expected prefix warning.
- [ ] `tstack ui` shows `herdrConfig` with the right layer.
- [ ] `tstack --help` lists `herdr`, and the pwsh completion offers it.
- [ ] `doc herdr` opens the knowledge base page after a sync.
- [ ] Start a herdr session, attach a Claude Code pane, detach, reattach, and

## Checklist E: Omarchy (Arch)

Omarchy is the biggest divergence. Everything in the repo's Linux bootstrap
assumes Debian: `bootstrap/_common-debian.sh` is apt-only, and there is no Arch
path today. A grep confirms the string "omarchy" appears nowhere in the repo.

- [ ] Decide the shape first: a new `bootstrap/omarchy-bootstrap.sh` with a shared
      `bootstrap/_common-arch.sh`, or a package-manager abstraction inside the
      existing common helper. Recommendation: a separate `_common-arch.sh`,
      because apt and pacman differ in more than the command name (no `-y`, group
      packages, and the AUR is a separate installer entirely).
- [ ] Work out the AUR question: is there an `herdr` or `herdr-bin` package, and
      is it published by Herdr, Inc. or by a third party? If it is third-party,
      use the official `install.sh` instead, the same call this repo makes on
      Windows.
- [ ] Omarchy manages its own `~/.config` with its own theme system
      (`omarchy-theme-set` and friends). Decide whether this stack's
      `resolvedTheme` wins, whether Omarchy's theme wins, or whether herdr's
      config is left unmanaged on Omarchy entirely. Two theme owners on one file
      is the same hazard as two writers on `settings.json`.
- [ ] Omarchy ships its own terminal, Alacritty or Ghostty depending on version,
      and Hyprland rather than WezTerm. Confirm which of this stack's
      WezTerm-dependent integrations degrade cleanly there. The
      `wezterm cli set-tab-title` calls are already guarded by `$WEZTERM_PANE`, so
      verify rather than assume.
- [ ] Omarchy already binds a large set of Hyprland shortcuts. Check the chosen
      herdr prefix and the stack's leader chord against them before committing to
      a default.
- [ ] zsh is not Omarchy's default shell in every release. Confirm what the
      bootstrap does when it finds bash or fish, and that it does not force a
      shell change without asking.
- [ ] Decide whether `tests/parity/run.sh` grows an Arch container. If it does, it
      must run on Arch's own Python, matching how the Debian and Ubuntu containers
      work.
- [ ] Confirm the same-source-tree invariant still holds: the `dot_*` files applied
      on Omarchy are the same ones applied on Ubuntu, and any Arch-only behaviour
      lives in the bootstrap or behind a runtime guard, never in a forked dotfile.
- [ ] Update `README.md`, `INSTALL.md` and `ARCHITECTURE.md`. "Three targets"
      becomes four, and the native-Linux language currently names Debian and
      Ubuntu explicitly.
