# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A chezmoi source tree that deploys a Windows 11 + WSL2 Ubuntu + native Linux (Debian/Ubuntu) terminal stack (WezTerm, tmux, Starship, zsh, PowerShell `$PROFILE`, Claude Code hooks/settings, modern CLI tools) from one git repo to three targets with a single `chezmoi apply`. On native Linux the `run_after` Windows-sync hook self-no-ops (no `/mnt/c/` mount), so the same source tree is correct everywhere.

There is no build, no test suite, no lint. "Running" the project means applying configs to the host machine.

## The apply workflow (this repo's equivalent of build/test)

Always run chezmoi **from inside WSL** (not from Windows). The post-apply hook needs a POSIX shell and `/mnt/c/...` to exist.

```sh
~/.local/bin/chezmoi diff      # preview pending changes (WSL targets only — see caveat below)
~/.local/bin/chezmoi apply -v  # apply; runs run_after_90-sync-windows.sh at the end
```

To capture a hand-edit that was made directly to the target (not the source):

```sh
chezmoi re-add ~/.zshrc
```

Only for files the stack owns outright. **Never `re-add` a part-owned file** — `~/.claude/settings.json` and `~/.cursor/hooks.json` hold another tool's state (see the strategy table below), and re-adding commits it to the template.

There is no CI. Verification is manual: `docs/verifying-changes.md` is the pre-commit checklist (syntax gates, headless WezTerm config load test, the byte-identical menu diff, throwaway config stores), and `INSTALL.md` § Phase 9 is the post-install smoke test for a fresh machine.

## The architectural twist: one source repo, three targets

chezmoi natively only manages `$HOME` on the machine where it runs. We need Windows `C:\Users\<you>\`, WSL `/home/<you>/`, and native Linux `/home/<you>/` covered by the same source tree. The solution:

1. **WSL- and native-Linux-targeted files** use chezmoi's standard `dot_*` / `dot_config/` / `executable_*` naming at the repo root → applied to `$HOME` normally. The same files cover both: WSL-specific code paths (e.g., `wezterm cli set-tab-title`) are already guarded by `$WEZTERM_PANE` and no-op outside WezTerm, so they're harmless on native Linux servers reached via ssh/PuTTY.
2. **Windows-targeted files** live under `windows/` and are **excluded** from chezmoi's apply by `.chezmoiignore` (`windows/**`).
3. **`run_after_90-sync-windows.sh`** walks `windows/` after each apply and mirrors every file to `/mnt/c/Users/<you>/<same relative path>`, with `.bak.YYYYMMDD[.N]` backups for any overwrite. **On native Linux the hook exits cleanly when `/mnt/c/Users/` is missing** — same script, three platforms.

**Bootstrap split.** `bootstrap/wsl-bootstrap.sh` (WSL) and `bootstrap/linux-bootstrap.sh` (native Debian/Ubuntu) both source the shared `bootstrap/_common-debian.sh` helper for the install steps (apt, oh-my-zsh, chezmoi, Starship, Nerd Font). The wrappers diverge only on Windows-username handling and the default `SOURCE_DIR`.

**Per-machine overrides.** `dot_zshrc` sources `~/.zshrc.local` at the end if it exists; `$PROFILE` dot-sources `Documents\PowerShell\profile.local.ps1` the same way. Neither is tracked by chezmoi — use them for peer-sync helpers, server-role aliases, `WORKSPACE_DIR` overrides, anything that shouldn't propagate. See `dot_zshrc.local.example` / `windows/Documents/PowerShell/profile.local.ps1.example` for the documented patterns.

**Workspace navigation** (`ws`/`wsp`/`wspu`/`wsw`, both shells) resolves at call time: `$WORKSPACE_DIR` if set, else the first existing autodetect candidate (`/mnt/c/DATA/Workspace`, `~/Documents/Workspace`, `~/workspace`, `~/Workspace`; pwsh probes `C:\DATA\Workspace`, `~\workspace`, `~\Documents\Workspace`). Don't convert this to chezmoi templating — `docs/decisions.md` § "Why `$WORKSPACE_DIR` + call-time resolution" explains why it must stay an env var. `wsp`/`wspu`/`wsw` are suffix siblings of that root (`_Personal`/`-Personal`, `_Public`/`-Public`, `_Work`/`-Work`); `wsw` additionally honours `$WORK_WORKSPACE_DIR` and can write it via `wsw --set`.

**Workspace organizer (`wso`).** Keeps repos in `<workspace>/<tier>/github.com/<owner>/<repo>` — implemented twice, `bootstrap/_workspace.sh` + `bootstrap/wso.sh` (bash: WSL/Linux/macOS) and `bootstrap/_workspace.ps1` + `bootstrap/_workspace_cmd.ps1` (pwsh: Windows). The two are parallel implementations, not a wrapper and a shim: change one, change the other, and keep `-h` output byte-identical. Both are chezmoi-ignored (`bootstrap/**`) and run from the clone, so `ts-update` ships fixes without a profile re-sync.

The layout map is `bootstrap/workspace.conf` — **tracked**, so all machines agree — with an untracked per-machine override at `~/.config/terminal-stack/workspace.local.conf` (`%LOCALAPPDATA%\terminal-stack\workspace.local.conf` on Windows) read second, winning key by key. It is whitespace-delimited `<directive> <key> <value>`, deliberately **not JSON**: bash cannot parse JSON without `jq`, and this stays diffable. Don't move it into chezmoi `[data]` — that store is built for scalars, and adding a key there has a 7-step blast radius across `_wizard.sh`, `_config.sh`, `.chezmoi.toml.tmpl`, `_config.ps1`, `ts-config.sh` and both sync scripts.

Two invariants worth not breaking. A repo's destination is derived from its `origin` remote, never the folder name — that is what catches misfiled and double-cloned repos, and `docs/decisions.md` explains why `local/` exists rather than guessing an owner for a remote-less repo. And the tier-name skip in `ts_ws_scan_candidates` / `Get-TsWsScanCandidates` applies **only directly under the workspace root**: a legacy sibling root can legitimately hold a repo named `public` or `local`, and skipping it there would silently drop a real repo from the migration plan.

The jump shortcuts (`ws37`/`ws42`/`wsmb`/`wsmd`/`wsar`/`wsj`, and the repointed `wspu`) must stay shell functions in `dot_zshrc` and `$PROFILE` — a child process cannot change the parent shell's directory.

**Runtime clone location.** The runtime clone — the one `ts-update` pulls and chezmoi applies from — lives at a canonical path: `%LOCALAPPDATA%\terminal-stack\stack` shared by Windows + WSL (WSL sees `/mnt/c/Users/<you>/AppData/Local/terminal-stack/stack`), `~/.local/share/terminal-stack` on native Linux/macOS; pins (`TERMINAL_STACK_DIR`) are only for non-canonical locations. Dev clones at workspace tier paths (e.g. the `wsmb` checkout at `src/github.com/martybytes/terminal-stack`) are **invisible** to resolution, doctor, and doc probes unless pinned — `ts-update` never touches the dev tree. Relocating a legacy-path clone is `ts-doctor --repair`'s job (`ts-update` only prints a notice); rationale in `docs/decisions.md` § "Runtime clone location: canonical app-data paths, invisible dev clones".

Three invariants there earned the hard way, all with `docs/decisions.md` entries:

- **The installers refuse a workspace-root target by default.** `wso migrate` derives a repo's destination from its `origin`, so a clone under the workspace root gets relocated to a tier path and orphans the install. Dev-clone tier paths stay exempt.
- **A *persisted* pin is honoured only while a clone lives at it.** `profile.local.ps1` is dot-sourced by `$PROFILE`, so `irm … | iex` never sees a clean environment — `install.ps1` compares the value against the persisted line to tell a leftover from a deliberate one-shot override. Don't "simplify" that back to `if ($env:TERMINAL_STACK_DIR)`.
- **A dangling env pin degrades, it never dead-ends.** `Resolve-TsSourceDir` / `_ts_src` fall through to the candidate search; an explicit `-SourceDir` still hard-fails. The asymmetry is deliberate.

And `wso` blocks migration of **any** un-tiered terminal-stack clone, not merely the one that resolves as active — `Get-TsWsRuntimeClone` returning `$null` is exactly the broken state where the guard is needed, so it must not be the thing that arms it.

**WezTerm mux domain (`ts-mux`).** Whether panes are hosted by `wezterm-mux-server` instead of the GUI is the saved setting `weztermMux` (`on`|`off`, **default off**). `bootstrap/ts-mux.sh` (zsh wrapper in `dot_zshrc`) and `Invoke-TsMux` in `$PROFILE` are parallel implementations — change one, change the other, keep `-h` byte-identical. Subcommands: `status` (setting vs. *rendered* setting vs. live server), `on`/`off` (persist + re-render), `list`, `kill`, `restart`, `reset`. The install wizard asks the question (`ts_prompt_wezterm_mux` / `Read-TsWeztermMux`, `TS_WEZ_MUX=on|off` to skip, skipped on headless hosts) and the three bash bootstraps persist it with `ts_wez_mux_set` right after `ts_save_config`. Unlike the other config keys it is stored on its own (`ts_wez_mux_set` / `Save-TsConfig -WeztermMux`) rather than through `ts_save_config`, so flipping it doesn't have to re-state every other choice. On WSL the mux server is a **Windows** process: the bash script reaches it through interop (`tasklist.exe`/`taskkill.exe`/`wezterm.exe`), never `pgrep`. Rationale in `docs/decisions.md` § "Why the mux domain is opt-in, not the default".

**WezTerm startup restore (`weztermRestore`).** Whether launching WezTerm replays the last autosaved session is the saved setting `weztermRestore` (`on`|`off`, **default off**), gated in both GUI configs behind `local RESTORE_ENABLED`. The resurrect block deliberately **does not call `resurrect.setup()`** — that helper registers `wezterm.on("gui-startup", …)` unconditionally with no opt-out, which is the whole bug; we drive `event_driven_save` + `periodic_save` directly and register the handler ourselves under the gate. Don't "simplify" it back. Autosave runs either way, so `Leader+S`/`Leader+L` are unaffected and `current_state` keeps tracking the live workspace. Asked by the wizard (`ts_prompt_wezterm_restore` / `Read-TsWeztermRestore`, `TS_WEZ_RESTORE=on|off`, skipped headless), persisted by the bash bootstraps with `ts_wez_restore_set`, flipped later with `ts-config restore on|off`. Rationale in `docs/decisions.md` § "Why the startup session restore is opt-in".

**atuin shell history (`atuinEnabled`).** Whether `Ctrl+R` is atuin's search instead of fzf's is the saved setting `atuinEnabled` (`on`|`off`, **default off**), asked by the wizard (`ts_prompt_atuin`, `TS_ATUIN=on|off`), persisted on its own with `ts_atuin_set` right after `ts_save_config`, and flipped later with `ts-config atuin on|off`. It is a **saved setting rather than a `command -v atuin` guard** on purpose: the binary is frequently already installed and completely dormant (a brew dependency, an old manual install), so a presence check would hijack `Ctrl+R` on the next apply without anyone choosing it — unlike zoxide/fzf, atuin *replaces* an existing binding. The switch is a chezmoi-rendered fragment, `dot_config/terminal-stack/atuin.zsh.tmpl` → `~/.config/terminal-stack/atuin.zsh`, which `dot_zshrc` sources unconditionally and which renders **empty** when off. **`dot_zshrc` must not become a `.tmpl`** to gate this inline: `chezmoi re-add ~/.zshrc` is a documented workflow above, and re-adding a rendered file into a template would clobber the directives — that is the whole reason for the fragment. The init line is sourced **after** `fzf --zsh` so atuin wins `Ctrl+R`; `--disable-up-arrow` leaves Up with oh-my-zsh's prefix search. **No pwsh twin and no winget id**, deliberately: `atuin init` has no PowerShell target (zsh/bash/fish/nu/xonsh only) and no winget manifest exists, so on Windows atuin lives in WSL — the same "honest not-available" rule as `ncdu`/`tree`/`bandwhich`. **The secret filter is duplicated and must stay in sync**: `dot_zshrc`'s `zshaddhistory()` returns 1 to discard secrets, but atuin records through its own `preexec` and never sees that hook, so `dot_config/atuin/config.toml.tmpl` repeats the same regexes in `history_filter` (plus `secrets_filter`). Change one, change the other, or secrets the stack refuses to write to `~/.zsh_history` start landing in atuin's SQLite database.

**Ghostty config (`ghosttyConfig`).** macOS-only managed `~/.config/ghostty/config` plus a `themes/vs-code-light-modern` the stack generates, gated by the saved setting `ghosttyConfig` (`on`|`off`, **default on**) and darwin-gated in `.chezmoiignore` beside `.wezterm.lua`. Driven by `ts-config ghostty on|off|status|diff`; **no pwsh twin** (Ghostty has no Windows build — same "absence is a decision" rule as `ts-smb`, stated in `-h`). Unlike Starship/tmux, the template reads **`{{ .themeMode }}`, not `{{ .resolvedTheme }}`**: Ghostty's `theme = dark:X,light:Y` follows the OS itself, so it joins WezTerm's live-switching class and `follow` needs no re-apply — reading `resolvedTheme` looks right and silently freezes `follow`. `Catppuccin Mocha` is a Ghostty builtin; **VS Code Light Modern is not**, so the light theme file is generated from `dot_wezterm.lua.tmpl`'s `PALETTES.light.scheme_def` and a test pins the two together. Two traps worth not re-introducing: **`off` must not be `.chezmoiremove`** — that is evaluated on every machine and would delete a hand-written Ghostty config on a box that never opted in, so `ts-config ghostty off` does the removal itself, for that machine only; and **`chezmoi apply` overwrites `$HOME` files with no backup on POSIX** (the `.bak.YYYYMMDD[.N]` convention only fires in the Windows sync hook and the merge helpers), so `run_before_20-backup-ghostty.sh` takes one first, skipping any file already carrying our marker so a managed config doesn't spawn a `.bak` every apply — that backup is what makes `off` a *restore* rather than a delete. Ghostty's config format has **no inline comments** (`#` after a value becomes part of the value), and `ghostty +validate-config` **exits 1** on error, unlike WezTerm's `show-keys`, so it is a real syntax gate. Still WezTerm-only: the tab bar. **Tab titles now work everywhere**, via `_ts_tab_title` / `Set-TsTabTitle` — WezTerm gets `wezterm cli set-tab-title` (a real sticky override), inside tmux we skip because tmux owns the outer title and substitutes `set-titles-string '#{s/^cc-//:session_name}'`, and everything else (Ghostty, Terminal.app) gets plain `OSC 2`. **The OSC 2 half only works because the `cc*` wrappers also set `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1`** — otherwise Claude Code writes `✳ Claude Code` and then its conversation slug straight over it, which is exactly the bug this fixed. Both halves are load-bearing; removing either silently restores the old behaviour. Ghostty's own sticky `set_tab_title` *does* survive Claude but is keybind-only — no CLI (`ghostty +new-window` reports "not supported on this platform") and no escape sequence reaches it (ConEmu `OSC 9;3` sets the *surface* title, tested). Inside tmux's `#{...}` the variable is `session_name`: `#{s/^cc-//:#S}` renders an **empty** title. Rationale in `docs/decisions.md` § "Why Ghostty gets a managed config after all".

**Claude/Cursor voice notifications (`ccTts*`).** Opt-in TTS (`ccTtsEnabled`, default off) speaks when Claude Code / Cursor finishes, errors, or needs input — engines Kokoro (Docker :8880) → Chatterbox → edge-tts → SAPI, config from `~/.claude/tts/config.json` + untracked `local.json`, module `bootstrap/_cc_tts.sh` + pwsh twins in `_config.ps1`, `ts-config tts …` both shells. Windows runtime is one GUI-subsystem **`terminal-stack-tts.exe`** at `%LOCALAPPDATA%\terminal-stack\tts-daemon` (PyInstaller build in `bootstrap/tts-daemon`; Python is build-time only). Windows Claude/Cursor/Codex hooks and WSL interop call that EXE directly — never reintroduce PowerShell, `cmd`, Python, `ffplay`, or `ffprobe` on the spoken hook path. Its optional tray daemon (`ccTtsDaemon`, default off) adds session naming, queue/coalesce, music duck/pause, and four summarizer modes (`self` marker-block edits the user's Claude `CLAUDE.md` and Codex global `AGENTS.md`, never whole-file-managing either; Cursor or stale sessions without a marker use a local final-response sentence); if the daemon is unavailable, the same EXE starts a detached in-process direct worker, preserving the **never silence** invariant. **One user-facing event can arrive as several hooks** — a Claude `AskUserQuestion` trips both `Notification` and the `AskUserQuestion` `PreToolUse` matcher, both `P0` (a third, `PermissionRequest`, was dropped: it echoed the tool name twice and `Notification` already announces permission prompts in Claude's own words) — so speech is deduplicated *across processes* through a SQLite utterance history (`state/history.db`): the daemon and every direct worker consult `recently_spoken(session, priority, debounceSec)` before speaking, and the direct path additionally holds an `O_CREAT|O_EXCL` play lock (`speaklock.py`) so two detached workers cannot overlap. The window is `debounceSec` in `~/.claude/tts/config.json` (5s, `0` disables dedupe) — deliberately *not* a new chezmoi `[data]` key. Read the record back with `ts-config tts history [--dupes]`; both shells run the same `terminal-stack-tts.exe history`, so there is no parallel implementation to keep byte-identical. A hook that finds the daemon enabled but not answering now **starts it** and retries once before falling back — autostart is logon-only, so a dead daemon used to degrade every hook to the unserialized direct path for the rest of the day. Everything on this path fails open: an unusable history DB, play lock or log directory must never stop an announcement, which is why `history.py`/`speaklock.py` swallow their own errors and `_setup_logging`/`_spawn_direct` keep their `mkdir` inside a guard. Rationale in `docs/decisions.md` § "Why duplicate speech is collapsed by a history table". **Going quiet is a sentinel file, not a config change**: `state/muted` (`ttsd/mute.py`) is written by `ccmute` in either shell, a left-click on the tray icon, the global hotkey (`hotkey` in `config.json`, default `ctrl+alt+shift+m`), `Leader+m` in WezTerm, or `POST /v1/mute`, and is read by `submit_hook`, `direct_speak`, the dispatcher and the native-WSL hook — so it holds with the daemon dead, survives a reboot, and is **absolute** (no `quietHours.allowInteractive` escape: silencing questions and permission prompts is the entire point). Muting also cuts off the utterance in flight via `Playback.stop()`. It fails *open* — an unreadable state dir means not muted, the opposite of `history.py`'s bias, because a mute you cannot lift is worse than one that fails audibly. The tray icon greys out and WezTerm shows a `MUTED` chip (polled at most 1×/s; `update-status` runs at 10 Hz), and `ts-doctor` reports both the mute and a `local.json` `enabled:false` mask — an unreported mute is indistinguishable from broken TTS. Not to be confused with `ccTtsEnabled`, which removes the hooks on the next apply. Rationale in `docs/decisions.md` § "Why the mute is a sentinel file, not the tray's DND". **A dashboard at `/ui`** (tray: Open dashboard) reports status, the decision timeline from `history.db`, and a live `ttsd.log` stream over SSE; the page is a string literal in `ttsd/webui.py` rather than a bundled asset, the follower never holds the log open (a held handle can break the daemon's own rotation on Windows), and every route refuses an unrecognised `Host` header because loopback is unauthenticated and any web page can reach 127.0.0.1. A Settings tab writes machine-local overrides to `local.json` (never chezmoi `[data]`, which the daemon cannot reach) and shows which layer won per field; validation lives in `ttsd/settings_schema.py`, the one list the server validates against and the page renders from, whose `restart` and `shell` flags are checked against the code by tests. **Mutating routes require `X-TS-Token` even on loopback** (the page carries it, same-origin, no CORS), which also closes a pre-existing hole where a cross-site form POST could mute the machine; `/v1/event`, `/v1/config/reload`, `/v1/duck/release` and `/v1/shutdown` stay open because hooks and the installer call them tokenless. The Anthropic key for `haiku` lives in `state/secrets.json` (`ttsd/keystore.py`), never in either config store, because a daemon started at logon cannot see an environment variable exported later. `POST /v1/summarizer/test` reports which mode *actually* ran, since haiku with no key is otherwise identical to template. Saved TTS changes reload a running daemon through `/v1/config/reload`; the executable itself is never auto-restarted (`ts-update` nudges; `ts-config tts daemon restart` is deliberate), and ducking keeps snapshot-before-change discipline. On combined Windows+WSL, run `ts-config tts …` from WSL so chezmoi `[data]` remains authoritative — a pwsh save writes **only** the `config.json` mirror, so the two stores silently diverge and the next `chezmoi apply` from WSL renders the setting back off (this is how all five Claude TTS hooks got removed on 2026-08-21, with no error and a diff that looked deliberate). If a saved setting reverts after an apply, compare the two stores before touching templates; `docs/decisions.md` § "Why config lives in chezmoi `[data]` + a Windows JSON mirror" has the commands. Any pwsh function that runs a child and returns status must stream via `| Out-Host`; bare `& pwsh` turns child output into truthy return data (`docs/powershell-quirks.md`).

**agentmemory harness wiring (`bootstrap/ts-agentmemory.ps1` + `ts-agentmemory.sh`).** **The bash twin is what makes macOS and Linux capture at all** — before it, those platforms served and searched but never wrote an observation, silently, because every vendor hook does `fetch(...).catch(() => {})` then `exit(0)` and `_doctor.sh`'s check was gated on `[ -d /mnt/c/Users ]`. `bootstrap/_agentmemory.sh` holds the edit definitions (keeping the `.ps1`'s `@T`/`@N` encoding so the two files' edit text diffs directly) and `_merge_json_settings.sh` ports the JSONC key-splice. Exactly **two** things differ from the `.ps1`, both mandatory: the stale-secret recovery reads the 0600 cache at `${XDG_CONFIG_HOME:-~/.config}/docker-local/agentmemory.secret` instead of `reg query HKCU\Environment`, which on Unix throws, is caught, and leaves the recovery a permanent no-op; and hook commands are a POSIX `VAR=value node "<path>"` prefix instead of a cmd.exe `set X=…&&` chain, which written into a hooks file on a Mac fails **silently**. The literal multi-line replace runs in **python3, not bash** — `${x//a/b}` treats the needle as a glob and `sed` is line-oriented and appends a trailing newline to a file that lacked one — and the file's line endings, not the matched form's, decide what gets inserted: a single-line anchor is byte-identical in LF and CRLF, so deciding from the match injects LF blocks into a CRLF file. Python must also read with `newline=""`, or universal-newline translation silently rewrites every CRLF vendor file to LF. Unlike the `.ps1`, which reports problems and still exits 0, the bash twin **exits non-zero in every mode** so `ts-agents.sh` can tell a clean apply from one where an edit's anchor had moved. Name it `bootstrap/ts-agentmemory.sh` exactly: `docker-local/agentmemory/check-capture.sh` probes for that path.

**agentmemory harness wiring, shared design (`bootstrap/ts-agentmemory.ps1`).** Wires Claude Code, Codex and Cursor to a local agentmemory server: the tagged `/_agent/<host>` URL, `AGENTMEMORY_INJECT_CONTEXT` **inlined** into every generated hook command (a User env var only reaches processes started after it was set, so inheriting it left long-running shells and desktop apps retrieving nothing), the deployment edits to the vendor hook scripts, and the duplicate-invocation guard. Edits live once in `bootstrap/_agentmemory.ps1` — the same six scripts exist twice for Codex (plugin cache for the CLI, `~/.codex/hooks/agentmemory` for Desktop) and again for Claude, and defining them per-installer is how the old Cursor script drifted into not reproducing its own installed state. **Auto-detected, with no saved setting**: a host is wired only when its agentmemory plugin cache is present, gated on the cache rather than server reachability so the wiring survives the container being stopped. Both sync paths run it (`-Check` first, `-Apply` only when something is missing), which is what makes a **plugin upgrade self-repairing** — an upgrade replaces the cache and silently reverts every edit, turning retrieval back off with nothing in any log. `ts-doctor` reports the same. Never put this wiring in `docker-local`: that repo is the Docker stack, and which hooks exist and what they run is this repo's concern (`docs/decisions.md` § "Why the agentmemory harness wiring lives here"). **Every agent gets prompt-level retrieval** (`/agentmemory/context` from `prompt-submit.mjs`, gated by `AGENTMEMORY_INJECT_CONTEXT`): it was Codex/Cursor-only on the theory that Claude already retrieved via `/enrich` at `PreToolUse` and `/session/start`, but `/enrich` fires only for the vendor allow-list, is excluded for `Bash`, and drops a path-less `Grep`/`Glob` — so a shell-heavy Claude session retrieved almost nothing (measured: 1041 captures against one `/context` in 5.7h). Claude's patch set therefore includes `prompt-submit.mjs`; adding a script to an agent's list is the whole change. **A 401 refreshes the secret and retries once**: a stale `AGENTMEMORY_SECRET` in a long-lived shell used to 401 every request for the life of that session, silently, because `/observe` swallows errors and retrieval discards non-2xx — 56 consecutive captures were lost that way on 2026-08-21. The recovery wraps `fetch` once per script rather than touching every call site, re-reads the authoritative value from the user environment, and fails open. The stack now *reads* the secret in two places — that recovery, and a `ts-doctor` check comparing the container's copy against the user environment (bounded by `timeout`, skipped when Docker is unreachable) — but still never writes it; the plugin's own `.mcp.json` owns that.

**Install catalog + agent CLIs.** `bootstrap/_config.sh` holds a flat catalog (`TS_APPS_RECOMMENDED`/`OPTIONAL`) plus a **groups layer that exists only for the picker** — `shell search disk system network git editors runtimes python ai` — so the saved `apps` array stays flat and no chezmoi `[data]` key is involved. The `ai` group (claude, codex, cursor-agent, grok, gemini, pi) **defaults to all and is still asked**; every group starts ticked and every tool stays individually untickable. Agent CLIs never come from a package manager, so they route through `ts_install_ai_cli` / `Install-TsAiCli`, not brew/apt/winget: claude, grok and cursor-agent have native installers needing no Node; codex (npm, Node 16+) and gemini (npm, Node 20+) are gated on the Node version and *say what to do* rather than failing. **No brew fallback for gemini** — that formula is deprecated upstream. **grok's installer appends a PATH line to `~/.zshrc`**, which this stack owns whole-file, so `GROK_BIN_DIR="$HOME/.local/bin"` routes it onto the already-managed PATH instead and `dot_zshrc` carries its completions `fpath` itself. Node is managed by **fnm** (not nvm: ~10ms of shell startup vs 200-500ms), wired into both shells with `--use-on-cd`; because fnm's PATH entry is created per-shell, `ts_apps_pending` and `ts_report_installed_apps` call `ts_load_node_env` first or they would nag about npm-installed CLIs forever.

**SMB shares (`ts-smb`).** Find, interrogate and mount SMB/CIFS shares through rclone, with one flag vocabulary on macOS and Linux (`bootstrap/ts-smb.sh` + `bootstrap/_smb.sh`, zsh wrapper in `dot_zshrc`). rclone is the transport for everything — `rclone lsd` against a host root enumerates its *shares*, so discovery and browsing are the same primitive — and on-the-fly connection strings (`:smb,host=…,user=…:`) mean interrogating a host needs no configuration at all. **There is deliberately no pwsh twin** (`docs/decisions.md` § "Why `ts-smb` ships without a PowerShell twin"); the `-h` prose says so, and the missing twin is a decision, not drift. The share store is `~/.config/terminal-stack/shares.local.conf` — untracked, machine-local, **never synced anywhere** — layered over a tracked `bootstrap/shares.conf` that holds defaults and never a host; the parser is cloned from `_workspace.sh`'s, stanza-shaped so its `read -r kind a rest` tokenizer is unchanged, and **the SMB share name is `path`, because `share` opens a stanza** (`ts_smb_validate` reports that trap by name). No chezmoi `[data]` key is added: this is a record list, not a scalar. **Passwords never touch argv** — there is no `--password VALUE` flag, only `-P` and `--password-stdin`; `ts-smb creds` obscures once at set time and stores the *obscured* blob in the OS keychain (macOS `security`, Linux `secret-tool`, with a 0600 file fallback), and it reaches rclone as `RCLONE_SMB_PASS`, which **must** be obscured or rclone rejects it. Three macOS facts are load-bearing and each cost real time to find: cgofuse picks its FUSE library by a fixed dlopen order with **no flag to override it**, so `ts-smb` always pins `CGOFUSE_LIBFUSE_PATH` (a stale macFUSE otherwise wins over a working FUSE-T and the mount *hangs* rather than failing); **Homebrew's macOS rclone cannot mount at all**, aborting with a build-time guard that no library or variable gets past, though browsing and copying are unaffected; and FUSE-T's **FSKit backend fails** on macOS 26.6 where its default NFS backend does not, so `-o backend=fskit` is never passed automatically. Mounts are tracked in `${XDG_STATE_HOME:-~/.local/state}/terminal-stack/smb/` for identity and intent, with **liveness derived from the kernel mount table, never stored** — and nothing may `stat`/`ls`/glob a mountpoint to test it, because a dead FUSE mount blocks forever and takes the shell with it. `ts-smb doctor` reports all of the above with the repair command; a gated three-line summary folds into `ts-doctor` once you actually have shares configured.

**Update/rollback.** `ts-update` records the pre-pull HEAD to a state file (`~/.local/state/terminal-stack/rollback-sha` / `%LOCALAPPDATA%\terminal-stack\rollback-sha`) before pulling; `ts-rollback` resets the clone to it and re-applies. Both refuse on a dirty clone. The state file is only written when commits are actually incoming.

Source → destination mapping for the `windows/` subtree is **relative-path-preserving**: `windows/.wezterm.lua` → `/mnt/c/Users/<you>/.wezterm.lua`. To add a new Windows-side file, drop it at the mirror path under `windows/` — no script changes needed. Full mechanism in `docs/cross-side-chezmoi.md`.

**Username resolution.** No source file hard-codes a username:

- WSL-side templates (`*.tmpl` under the chezmoi source root, e.g. `dot_config/starship.toml.tmpl`) use chezmoi's native engine — `{{ .chezmoi.homeDir }}`, `{{ .chezmoi.username }}`.
- Windows-side templates (`*.tmpl` under `windows/`, e.g. `windows/.claude/settings.json.tmpl`) use a literal `__WIN_USER__` token that `run_after_90-sync-windows.sh` substitutes at sync time. The username is resolved from (1) `chezmoi data → windowsUsername` (written by the WSL bootstrap), falling back to (2) `cmd.exe /c echo %USERNAME%` via WSL interop. When you add a new Windows-side templated file, use `__WIN_USER__` — not Go-template syntax.

**User config tokens.** The sync hook (and `scripts/sync-windows.ps1`) substitute more than `__WIN_USER__` into Windows-side `.tmpl` files, sourced from the saved config: `__LEADER_KEY__`, `__LEADER_MODS__` (WezTerm leader), `__THEME_MODE__` (`dark`|`light`|`follow`), `__THEME_RESOLVED__` (baked palette `light`|`dark`), `__TMUX_PREFIX__`, `__WEZ_MUX__` (`on`|`off`, the WezTerm mux domain), `__WEZ_RESTORE__` (`on`|`off`, reopen the last session at startup). WSL/native chezmoi templates read the same values as `{{ .leaderKey }}` / `{{ .leaderMods }}` / `{{ .themeMode }}` / `{{ .resolvedTheme }}` / `{{ .tmuxPrefixResolved }}` / `{{ .weztermMux }}` / `{{ .weztermRestore }}` — always behind a `hasKey` guard with a default, so a clone predating the wizard renders today's look (Ctrl+Space, Mocha, mux off, no startup restore). The choices live in chezmoi `[data]` (mirrored to `%LOCALAPPDATA%\terminal-stack\config.json` for Windows-standalone); `.chezmoi.toml.tmpl` re-emits the raw choices and derives the bindings, `resolve_os_theme` (in `bootstrap/_config.{sh,ps1}`) computes `resolvedTheme`. Rendering the Windows-side `.tmpl`s in the WSL hook **requires python3** (the old sed fallback was removed — it couldn't render the multi-line `__CC_TTS_*__` tokens and broke on two-modifier leaders). Wizard = `bootstrap/_wizard.sh` + pwsh prompts in `_config.ps1`; change later via `bootstrap/ts-config.sh` (zsh `ts-config`) / pwsh `Set-TerminalStackConfig`. Every question goes through one menu helper — `Read-TsChoice` (pwsh) / `ts_prompt_choice` (bash), parallel implementations whose **rendered output must stay byte-identical** (diff the two menus; same rule as `wso`). They mark the default, accept an option's name as well as its number, and **re-prompt on invalid input** rather than falling into it — don't restore a `default:` catch-all. `TS_WIZ_ASKED` is tallied in `ts_wizard_ask`, never inside `ts_prompt_choice`: prompts run through `$(…)`, so a subshell increment is discarded. The terminal emulator is a wizard choice, **not** a required package: a tick-list (`ts_prompt_terminals` / `Read-TsTerminals`) with **WezTerm nightly, WezTerm stable and Ghostty as separate ticks**, `[n]one` one keystroke away. **Whatever is installed starts ticked, on its detected channel** (`ts_wezterm_channel`, read back from the package manager); nightly is the pre-selection only when nothing is installed — upstream's newest stable is `20240203` (Feb 2024, no cut since) and the Lua config targets current builds. So a box that already has stable sees nightly *unticked*, which reads like a bug and has been reported as one; it is a re-run offering to upgrade what you have rather than switch your channel behind you. The two channels are **mutually exclusive in the tick-list itself** (`TS_MULTI_EXCLUSIVE` / `-Exclusive`) — both casks own `/Applications/WezTerm.app` — so ticking one unticks the other on screen rather than the list showing `[x] [x]` for a combination the code silently refuses. And **nothing is automatic**: the wizard asks, `ts-update` offers when something newer exists, `ts-config wezterm` changes it. The channel is **not a saved setting**: it is read back from the package manager (brew cask / winget id / dpkg package), so there is still no `weztermChannel` key. Facts come from `bootstrap/_wezterm.sh` (POSIX) / the `*-TsWez*` functions in `_config.ps1`: the build date is *in* the release name, latest-nightly is the `updated_at` of **this platform's** nightly asset (the rolling tag's own date is stuck in 2019), and "what changed" is sliced from upstream's `docs/changelog.md` at the heading matching your version — no LLM. Every network call fails open with a timeout. Env var `TS_TERMINALS=wezterm-nightly,wezterm-stable,ghostty|none`; `TS_WEZTERM=nightly|stable|skip` still maps across. Rationale in `docs/decisions.md` §§ "Why the WezTerm channel is a question, and why it is not a saved setting" / "Why config lives in chezmoi `[data]` + a Windows JSON mirror" / "Why WezTerm follows the OS theme live, but Starship/tmux bake at apply time".

**WezTerm config.** The two GUI configs (`windows/.wezterm.lua.tmpl` for Windows, `dot_wezterm.lua.tmpl` for macOS) must stay visually in sync; the pane-nav module (`windows/.wezterm/pane_nav.lua` ↔ `dot_wezterm/pane_nav.lua`, kept in sync) drives the F1–F4 direction keys (focus the pane that way, or split one there), F5/F6 PaneSelect jump/swap, Shift+F1–F4 domain splits, and the Leader+1–6 mirrors. **The tab bar is the fancy bar, fully hand-rolled** (tabline.wez was dropped — `docs/decisions.md` § "Why the tab bar is fancy and fully hand-rolled"): the retro bar's height is locked to one terminal cell and WezTerm has no multi-line bar, so `use_fancy_tab_bar = true` + `window_frame.font_size` give a taller bar, with tabs (`format-tab-title`) and status (`update-status`) drawn by our own Lua. The active tab is a solid accent block; inactive tabs with Claude panes wash with their `cc_state` tint; labels are short on purpose — the bare project leaf for Claude panes (the cc wrappers/hooks set **no `cc` prefix** any more; `strip_cc_prefix` cleans titles from not-yet-updated machines), a ` host ·` chip + directory leaf for remote panes, never a full path. The status bar is **quiet by default**: the left side renders *nothing* in the normal state (no permanent 'NORMAL' badge — a coloured badge appears only while the leader is pending or a repeat mode is live), and the right side shows the Claude fleet counts (`cc_state` across every mux pane), the non-default workspace, and a clock; Leader+s (`wezterm.GLOBAL.show_identity`) toggles the `user@host │ path` detail only. The remaining plugins — Leader+p project picker (sessionizer.wezterm) and Leader+S/L session save/restore (resurrect.wezterm) — load from **pinned forks under `github.com/martybytes`**, each `pcall`-guarded so a failed clone only loses its binding. Windows renders with OpenGL (WebGpu crashed — see `docs/decisions.md`). The mux domain (`unix_domains` + `default_domain = 'main'`) is **opt-in and off by default**, gated in both configs behind `local MUX_ENABLED` (`__WEZ_MUX__` on the Windows mirror, `{{ .weztermMux }}` on macOS) and driven by `ts-mux` (see **WezTerm mux domain** above). `.wezterm/**` is darwin-gated in `.chezmoiignore`.

**Important caveat:** `chezmoi diff` only shows changes to WSL targets. It does NOT show what the `run_after` hook will sync to `/mnt/c/`. To preview Windows-side changes, compare source manually or just run apply and read the `created`/`updated` lines.

## File-management strategies (don't mix them up)

| File | Strategy | Why |
|---|---|---|
| `~/.zshrc` | whole-file | We own every line (oh-my-zsh template + our additions) |
| `~/.claude/settings.json` (Windows) | **key-splice merge** (`bootstrap/_merge_claude_settings.ps1`) | We own only `statusLine`, `hooks`, `theme` — whatever `windows/.claude/settings.json.tmpl` renders. Claude Code writes the same file (`model`, `enabledPlugins`, `permissions`, `env`, `extraKnownMarketplaces`), so the sync splices our keys in and leaves every other byte alone |
| `~/.claude/settings.json` (WSL/macOS/Linux) | **key-splice merge** (`dot_claude/modify_settings.json.tmpl`) | Same ownership as the Windows row — `statusLine`, `hooks`, `theme`, derived from the rendered fragment, never a hard-coded list. It was a whole-file target until macOS-side Claude Code grew `agentPushNotifEnabled` and an apply started deleting it; the chezmoi `modify_` script gets the live file on stdin and returns it with only our keys replaced. An unparseable live file is echoed back untouched rather than overwritten |
| `~/.cursor/hooks.json` (Windows) | **per-entry splice** (`bootstrap/_merge_cursor_hooks.ps1`) | Everything lives under one `hooks` key and other tools use the same event arrays — agentmemory's Cursor hooks share `stop` and `postToolUse` with our TTS hooks. Ownership is per *entry* (matched on `terminal-stack` / `cursor-tts` / the `cat > /dev/null` no-op), so a key splice is not enough |
| `~/.tmux.conf`, `~/.config/starship.toml`, `~/.wezterm.lua` | whole-file **template** (`.tmpl`) | We own it; templated for leader/theme/prefix from chezmoi `[data]` (or `__TOKEN__`s on the Windows mirror). Edit the `.tmpl`, not the rendered file |
| `~/.config/git/terminal-stack.gitconfig` (both sides) | whole-file | We own it; hooked via `include.path`, user's `~/.gitconfig` stays untouched and wins |
| `$PROFILE` (Windows pwsh) | whole-file sync, **marker-block edited** | The sync copies the repo file over `$PROFILE` whole (with `.bak`); the `# ---- name-start ----` / `# ---- name-end ----` blocks organize the stack's regions. Personal content belongs in `profile.local.ps1`, never in `$PROFILE` itself |
| `~/.zshrc.local`, `profile.local.ps1`, `~/.doc.local/**` | **never managed** | Per-machine; `.zshrc.local`/`profile.local.ps1` ship `.example` twins; `~/.doc.local` is the personal `doc` layer |

**The `doc` knowledge base.** Command docs are plain `.md` files under `docs/kb/` in the clone (`common/`, `linux/`, `macos/`, `windows/`, `wezterm/`). On Windows, `scripts/sync-windows.ps1` (and the WSL `run_after` hook) also mirror `docs/kb/**` to `%LOCALAPPDATA%\terminal-stack\docs\kb\` so `doc`/`wzr` pick up updates after sync/apply; clone paths (`$TERMINAL_STACK_DIR`, workspace probes) still win for `doc edit`/`doc sync`. `docs/**` is chezmoi-ignored — canonical source stays in the clone. Per-machine/secret content lives in the untracked `~/.doc.local/` layer. `ref` and `wzr` are thin aliases into `doc`.

When modifying `$PROFILE`, edit the repo source (`windows/Documents/PowerShell/Microsoft.PowerShell_profile.ps1`) **inside an existing marker block** (`starship-stack-*`, `cli-tools-*`, `git-shortcuts-*`, …) or add a new marker block; keep `local-overrides` last. Anything a user hand-adds to the live `$PROFILE` outside the repo is replaced on the next sync (backed up, but gone from the live file) — per-machine content goes in `profile.local.ps1`. History in `docs/decisions.md` § "Why a whole-file `~/.zshrc` and a marker-block `$PROFILE`?".

## Gotchas worth remembering

These are written up at length in `docs/powershell-quirks.md`; the short version:

- **CRLF drift.** The repo's `.gitattributes` (`* text=auto eol=lf`) overrides Windows' `core.autocrlf=true` and forces LF in the working tree on every platform. Without it, every chezmoi-source file on a Windows clone gets CRLF on checkout, which breaks `~/.zshrc` under zsh (`^M` errors), `run_after_90-sync-windows.sh` (`#!/usr/bin/env bash\r` is not executable), and produces spurious `.bak` files on every apply. Don't remove `.gitattributes`. Rescue path for a single file that slipped through (e.g., an editor that ignored attributes): `sed -i 's/\r$//' <file>` from inside WSL.
- **Never whole-file-copy a settings file its own app also writes.** `~/.claude/settings.json` holds Claude Code's own state (`model`, `enabledPlugins`, `permissions`, `env`) next to our `statusLine`/`hooks`/`theme`, and a whole-file mirror deletes it with no error and nothing in the diff — that is how the agentmemory plugin got silently disabled (`enabledPlugins` vanished mid-session, so its hooks and MCP server stopped loading). The same sync emptied `~/.cursor/hooks.json` of agentmemory's seven Cursor hooks. Both files now route through a merge helper on both sync paths (`bootstrap/_merge_claude_settings.ps1`, `bootstrap/_merge_cursor_hooks.ps1`). If you add another such file, splice it; don't copy it — and check whether ownership is per key or, as with Cursor's shared event arrays, per entry. Details in `docs/decisions.md` §§ "Why `~/.claude/settings.json` is spliced, not copied" / "Why `~/.cursor/hooks.json` needs per-entry ownership".
- **JSON paths in Claude Code hooks must use forward slashes**, not backslashes. Two shell layers strip backslashes; forward slashes survive. See `windows/.claude/settings.json.tmpl` for examples (`C:/Users/__WIN_USER__/.claude/hooks/...`).
- **Tab title for `cc` wrappers uses `wezterm cli set-tab-title`, not OSC 0.** Claude Code's TUI overwrites `pane.title` (OSC) with its conversation slug; `tab.tab_title` is sticky and survives. The `format-tab-title` hook in both WezTerm configs checks `tab.tab_title` first, falling back to the active pane's cwd leaf.
- **Never auto-restart `wezterm-mux-server`.** When the mux is on, the server loads its own copy of `.wezterm.lua`, so a config change doesn't reach it — but restarting it kills every live pane. The sync scripts print a reminder instead (and only when `weztermMux` is `on`); `ts-mux restart` is the deliberate, confirmed path. Keep it that way.
- **`Enable-TransientPrompt` is guarded with `Get-Command`** because PSReadLine 2.4.5 doesn't export it. Don't remove the guard.
- **Never pipe `Where-Object` straight into `Set-Content`.** An empty pipeline gives `Set-Content` no value to write, so it leaves the file untouched — silently, with no error. Filtering a file down to nothing therefore *keeps* the line you meant to remove. Collect into an array and pass `-Value` (`@()` truncates as intended). A `-replace` pipeline is safe; it can't go empty.
- **`doc`'s alt-e edit binding can't hard-code fzf's `become(...)` action.** `become` (replace the fzf process with `$EDITOR`) only exists in fzf 0.42.0+; Debian/Ubuntu `apt` (what `_common-debian.sh` installs) ships older fzf (e.g. 0.29 on Ubuntu 22.04), where it's an unrecognized action and fzf refuses to start with `unknown action: become(...)`. `_doc_finder` in `dot_zshrc` resolves the bind through `_doc_edit_bind`, which checks the installed fzf version (zsh's `is-at-least`) and falls back to `execute(${EDITOR:-micro} {2})+abort` below 0.42.0 — the same fallback the pwsh side (`Invoke-DocFinder`) already used unconditionally. Don't revert to a bare `become(...)` bind.

## Backup convention

Any script in this repo that overwrites a user file must write a backup first as `<path>.bak.YYYYMMDD`. If that name already exists (same-day re-run), append `.1`, `.2`, etc. Never clobber a same-day backup. Reference implementation: `run_after_90-sync-windows.sh:28-34`. A Phase 7 incident where this discipline was missing motivated the hardening; see `docs/decisions.md` § "Why two backups".

## Personal-path note

The source tree carries no hard-coded usernames. The WSL bootstrap prompts for the Windows username (default = interop-detected) and persists it under `[data].windowsUsername` in `~/.config/chezmoi/chezmoi.toml`; the sync hook substitutes it into `windows/**/*.tmpl` files at apply time, and WSL-side templates use chezmoi's native `{{ .chezmoi.homeDir }}`. If you ever see a literal username in a source file, that's a regression — replace it with `__WIN_USER__` (Windows side) or `{{ .chezmoi.homeDir }}` (WSL side, file needs `.tmpl` suffix).
