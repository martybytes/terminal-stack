# CLAUDE.md

Architecture and invariants. Process rules (which clone, what to commit, how to push) are in `AGENTS.md`.

**This file is capped at 40 KB** (`test_claude_instructions_fit_claude_code_limit`) and runs close to it, because it loads into every session. Adding a section means **displacing** one: keep the invariant and the trap here, move the narrative and the measurements to `docs/decisions.md`, leave a `§` pointer.

## What this repo is

A chezmoi source tree that deploys a Windows 11 + WSL2 Ubuntu + native Linux (Debian/Ubuntu) terminal stack (WezTerm, tmux, Starship, zsh, PowerShell `$PROFILE`, Claude Code hooks/settings, modern CLI tools) from one git repo to three targets with a single `chezmoi apply`. On native Linux the `run_after` Windows-sync hook self-no-ops (no `/mnt/c/` mount), so the same source tree is correct everywhere.

"Running" the project means applying configs to the host. Gates: `pytest tests/`, `ruff check` / `ruff format --check` / `mypy` (`pyproject.toml`), CI (`.github/workflows/ci.yml`: ubuntu + macos + windows + WSL + parity containers), `.githooks/pre-commit` and `pre-push`.

**Verify a claim before repeating it.** Every "X is pinned by a test" here was checked against `tests/`; several were false, one of which meant no gate ran at all. See `docs/decisions.md` § "The claims audit".

## The apply workflow (this repo's equivalent of build/test)

Always run chezmoi **from inside WSL** (not from Windows). The post-apply hook needs a POSIX shell and `/mnt/c/...` to exist.

```sh
~/.local/bin/chezmoi diff      # preview pending changes (WSL targets only — see caveat below)
~/.local/bin/chezmoi apply -v  # apply; runs run_after_90-sync-windows.sh at the end
```

To capture a hand-edit that was made directly to the target (not the source):

```sh
chezmoi re-add ~/.zshrc
```

**The one `re-add` rule.** Correct **only** when the stack owns the target outright **and** its source is not a template. `~/.zshrc`: safe. Part-owned (`~/.claude/settings.json`, `~/.cursor/hooks.json`): never, they hold another tool's state. Templated (`*.tmpl` source): never, re-add writes back the *rendered* file and destroys the directives. ARCHITECTURE.md and AGENTS.md each state one case; scope was the missing word.

CI covers macOS, which no local run can; `tests/parity/run.sh` covers native Debian/Ubuntu locally in containers, on each distro's own Python. It does not replace `docs/verifying-changes.md`, which holds what a machine cannot assert for you (headless WezTerm load test, throwaway config stores, the Nerd Font glyph check); `INSTALL.md` § Phase 9 is the fresh-machine smoke test.

## The architectural twist: one source repo, three targets

chezmoi natively only manages `$HOME` on the machine where it runs. We need Windows `C:\Users\<you>\`, WSL `/home/<you>/`, and native Linux `/home/<you>/` covered by the same source tree. The solution:

1. **WSL- and native-Linux-targeted files** use chezmoi's standard `dot_*` / `dot_config/` / `executable_*` naming at the repo root → applied to `$HOME` normally. The same files cover both: WSL-specific code paths (e.g., `wezterm cli set-tab-title`) are already guarded by `$WEZTERM_PANE` and no-op outside WezTerm, so they're harmless on native Linux servers reached via ssh/PuTTY.
2. **Windows-targeted files** live under `windows/` and are **excluded** from chezmoi's apply by `.chezmoiignore` (`windows/**`).
3. **`run_after_90-sync-windows.sh`** walks `windows/` after each apply and mirrors every file to `/mnt/c/Users/<you>/<same relative path>`, with `.bak.YYYYMMDD[.N]` backups for any overwrite. **On native Linux the hook exits cleanly when `/mnt/c/Users/` is missing** — same script, three platforms.

**Bootstrap split.** `bootstrap/wsl-bootstrap.sh` (WSL) and `bootstrap/linux-bootstrap.sh` (native Debian/Ubuntu) both source the shared `bootstrap/_common-debian.sh` helper for the install steps (apt, oh-my-zsh, chezmoi, Starship, Nerd Font). The wrappers diverge only on Windows-username handling and the default `SOURCE_DIR`.

**Per-machine overrides.** `dot_zshrc` sources `~/.zshrc.local` at the end if it exists; `$PROFILE` dot-sources `Documents\PowerShell\profile.local.ps1` the same way. Neither is tracked by chezmoi — use them for peer-sync helpers, server-role aliases, `WORKSPACE_DIR` overrides, anything that shouldn't propagate. See `dot_zshrc.local.example` / `windows/Documents/PowerShell/profile.local.ps1.example` for the documented patterns.

**Workspace navigation** (`ws`/`wsp`/`wspu`/`wsw`, both shells) resolves at call time: `$WORKSPACE_DIR` if set, else the first existing autodetect candidate (`/mnt/c/DATA/Workspace`, `~/Documents/Workspace`, `~/workspace`, `~/Workspace`; pwsh probes `C:\DATA\Workspace`, `~\workspace`, `~\Documents\Workspace`). Don't convert this to chezmoi templating — `docs/decisions.md` § "Why `$WORKSPACE_DIR` + call-time resolution" explains why it must stay an env var. `wsp`/`wspu`/`wsw` are suffix siblings of that root (`_Personal`/`-Personal`, `_Public`/`-Public`, `_Work`/`-Work`); `wsw` additionally honours `$WORK_WORKSPACE_DIR` and can write it via `wsw --set`.

**Workspace organizer (`wso`).** Keeps repos in `<workspace>/<tier>/github.com/<owner>/<repo>` — implemented twice, `bootstrap/_workspace.sh` + `bootstrap/wso.sh` (bash: WSL/Linux/macOS) and `bootstrap/_workspace.ps1` + `bootstrap/_workspace_cmd.ps1` (pwsh: Windows). The two are parallel implementations, not a wrapper and a shim: change one, change the other, and keep `-h` output byte-identical. Both are chezmoi-ignored (`bootstrap/**`) and run from the clone, so `tstack update` ships fixes without a profile re-sync.

The layout map is `bootstrap/workspace.conf` — **tracked**, so all machines agree — with an untracked per-machine override at `~/.config/terminal-stack/workspace.local.conf` (`%LOCALAPPDATA%\terminal-stack\workspace.local.conf` on Windows) read second, winning key by key. It is whitespace-delimited `<directive> <key> <value>`, deliberately **not JSON**: bash cannot parse JSON without `jq`, and this stays diffable. Don't move it into chezmoi `[data]` — that store is built for scalars, and adding a key there has a 7-step blast radius across `_wizard.sh`, `_config.sh`, `.chezmoi.toml.tmpl`, `_config.ps1`, `ts-config.sh` and both sync scripts.

Two invariants worth not breaking. A repo's destination is derived from its `origin` remote, never the folder name — that is what catches misfiled and double-cloned repos, and `docs/decisions.md` explains why `local/` exists rather than guessing an owner for a remote-less repo. And the tier-name skip in `ts_ws_scan_candidates` / `Get-TsWsScanCandidates` applies **only directly under the workspace root**: a legacy sibling root can legitimately hold a repo named `public` or `local`, and skipping it there would silently drop a real repo from the migration plan.

The jump shortcuts (`ws37`/`ws42`/`wsmb`/`wsmd`/`wsar`/`wsj`, and the repointed `wspu`) must stay shell functions in `dot_zshrc` and `$PROFILE` — a child process cannot change the parent shell's directory.

**Runtime clone location.** The runtime clone — the one `tstack update` pulls and chezmoi applies from — lives at a canonical path: `%LOCALAPPDATA%\terminal-stack\stack` shared by Windows + WSL (WSL sees `/mnt/c/Users/<you>/AppData/Local/terminal-stack/stack`), `~/.local/share/terminal-stack` on native Linux/macOS; pins (`TERMINAL_STACK_DIR`) are only for non-canonical locations. Dev clones at workspace tier paths (e.g. the `wsmb` checkout at `src/github.com/martybytes/terminal-stack`) are **invisible** to resolution, doctor, and doc probes unless pinned — `tstack update` never touches the dev tree. Relocating a legacy-path clone is `tstack doctor --repair`'s job (`tstack update` only prints a notice); rationale in `docs/decisions.md` § "Runtime clone location: canonical app-data paths, invisible dev clones".

Three invariants there earned the hard way, all with `docs/decisions.md` entries:

- **The installers refuse a workspace-root target by default.** `wso migrate` derives a repo's destination from its `origin`, so a clone under the workspace root gets relocated to a tier path and orphans the install. Dev-clone tier paths stay exempt.
- **A *persisted* pin is honoured only while a clone lives at it.** `profile.local.ps1` is dot-sourced by `$PROFILE`, so `irm … | iex` never sees a clean environment — `install.ps1` compares the value against the persisted line to tell a leftover from a deliberate one-shot override. Don't "simplify" that back to `if ($env:TERMINAL_STACK_DIR)`.
- **A dangling env pin degrades, it never dead-ends.** `Resolve-TsSourceDir` / `_ts_src` fall through to the candidate search; an explicit `-SourceDir` still hard-fails. The asymmetry is deliberate.

And `wso` blocks migration of **any** un-tiered terminal-stack clone, not merely the one that resolves as active — `Get-TsWsRuntimeClone` returning `$null` is exactly the broken state where the guard is needed, so it must not be the thing that arms it.

**WezTerm mux domain (`tstack mux`).** Whether panes are hosted by `wezterm-mux-server` instead of the GUI is the saved setting `weztermMux` (`on`|`off`, **default off**). `tstack/commands/mux.py` is the one implementation; the bash and pwsh twins are deleted. Subcommands: `status` (setting vs. *rendered* setting vs. live server), `on`/`off` (persist + re-render), `list`, `kill`, `restart`, `reset`. The install wizard asks the question (`ts_prompt_wezterm_mux` / `Read-TsWeztermMux`, `TS_WEZ_MUX=on|off` to skip, skipped on headless hosts) and the three bash bootstraps persist it with `ts_wez_mux_set` right after `ts_save_config`. Unlike the other config keys it is stored on its own (`ts_wez_mux_set` / `Save-TsConfig -WeztermMux`) rather than through `ts_save_config`, so flipping it doesn't have to re-state every other choice. On WSL the mux server is a **Windows** process, so it is reached through interop (`tasklist.exe`/`taskkill.exe`/`wezterm.exe`), never `pgrep` - which finds nothing inside WSL while a healthy server runs on the same machine. Rationale in `docs/decisions.md` § "Why the mux domain is opt-in, not the default".

**WezTerm startup restore (`weztermRestore`).** Whether launching WezTerm replays the last autosaved session is the saved setting `weztermRestore` (`on`|`off`, **default off**), gated in both GUI configs behind `local RESTORE_ENABLED`. The resurrect block deliberately **does not call `resurrect.setup()`** — that helper registers `wezterm.on("gui-startup", …)` unconditionally with no opt-out, which is the whole bug; we drive `event_driven_save` + `periodic_save` directly and register the handler ourselves under the gate. Don't "simplify" it back. Autosave runs either way, so `Leader+S`/`Leader+L` are unaffected and `current_state` keeps tracking the live workspace. Asked by the wizard (`ts_prompt_wezterm_restore` / `Read-TsWeztermRestore`, `TS_WEZ_RESTORE=on|off`, skipped headless), persisted by the bash bootstraps with `ts_wez_restore_set`, flipped later with `tstack config restore on|off`. Rationale in `docs/decisions.md` § "Why the startup session restore is opt-in".

**Wizard recommendations and readiness probing.** Every behaviour question opens with a `RECOMMENDATION:` line saying which way to go *and what it costs* (mux **off**, session restore **off**, atuin **on**). The **agent toggles are probed, not guessed** — a machine wired to a service that is not running captures nothing and reports nothing, silently. **"Answering" is the test, never a 2xx**: AgentMemory returns 404 on `/` and 401 on `/agentmemory/health`, so `ts_probe_http` accepts any HTTP status and only a refused connection counts as down; `ts_probe_http_ok` is the strict variant for real readiness endpoints. Costs, defaults and the incident behind the probe: `docs/decisions.md` § "Why every wizard question carries a recommendation". Headroom MCP runs on demand through Docker stdio; `tstack agents` verifies JSON-RPC initialize before registration, while port `8788` stays dashboard-only. `ts_app_installable` keeps platform-impossible ids (`nvtop` on macOS) out of `ts_apps_pending`, which otherwise nagged on every `tstack update` and could never succeed.

**Which prompt (`starshipPreset`).** `terminal-stack` (**default**) is this repo's own prompt; anything else is a Starship built-in preset, and `tstack config prompt list` **renders every option live**. **Not vendored**: `dot_config/starship.toml.tmpl` runs `starship preset` at apply time behind `lookPath`, because a bootstrap can render it before starship exists and chezmoi's `output` on a missing binary aborts the *whole* apply. Both syncs cover the Windows side or a combined machine shows two prompts. Traps: `-o` refuses to overwrite the file `mktemp` just made; `STARSHIP_SHELL` must be **empty, not unset**; an unknown name renders an **empty** config, so it is checked against `starship preset --list` before saving; and that template's closing `{{ end -}}` must not gain a leading dash or it eats the trailing newline.

**The wizard's first two questions** are `TS_PROFILE` (`prompt|shell|full`, opening with the prompt rendered live) and `TS_DEVELOPMENT`. **Neither is saved**: they decide what the rest of the wizard asks and what those answers default to, and every one of *those* is saved on its own. On `prompt` the rest is pinned, and the review lists it. Twins: `ts_prompt_profile`/`ts_prompt_development`, `Read-TsProfile`/`Read-TsDevelopment`.

**`tstack ui`** is the Textual settings dashboard — every setting, its default, and **which layer the value came from**. It **never writes the store**: saves route through `config.set_value`, so one writer and one set of rules. Textual is the only third-party import in `tstack` and only this command uses it, so it is optional and isolated in `tstack/ui/`. `app.py` is excluded from coverage *measurement*, not testing; its tests live in their own module because `importorskip` skips the file it is in.

**atuin shell history (`atuinEnabled`).** Whether `Ctrl+R` is atuin's search instead of fzf's: `on`|`off`, **default off**, asked by the wizard (`TS_ATUIN`), persisted on its own with `ts_atuin_set`, flipped with `tstack config atuin on|off`. A **saved setting rather than a `command -v atuin` guard** on purpose: the binary is frequently already installed and dormant, and unlike zoxide/fzf atuin *replaces* an existing binding, so a presence check would hijack `Ctrl+R` on the next apply without anyone choosing it. It is a chezmoi-rendered fragment (`dot_config/terminal-stack/atuin.zsh.tmpl`) that `dot_zshrc` sources unconditionally and that renders **empty** when off - **`dot_zshrc` must not become a `.tmpl`** (see the re-add rule above). **The secret filter is duplicated and must stay in sync**: `dot_zshrc`'s `zshaddhistory()` discards secrets, but atuin records through its own `preexec` and never sees that hook, so `dot_config/atuin/config.toml.tmpl` repeats the same regexes in `history_filter`. No pwsh twin and no winget id, deliberately: `atuin init` has no PowerShell target. Rationale in `docs/decisions.md`.

**Ghostty config (`ghosttyConfig`).** Managed `~/.config/ghostty/config` (macOS, chezmoi, darwin-gated) **and `%LOCALAPPDATA%\ghostty\config` (Windows, via the `windows/AppData/Local/ghostty/` mirror)**, plus a generated `themes/vs-code-light-modern`. Saved setting `ghosttyConfig` (`on`|`off`, **default on**); `tstack config ghostty on|off|status|diff` has a pwsh twin and works from WSL. **Target `%LOCALAPPDATA%\ghostty\`, never the app-named dir** - `<appname>` flips on the noctty rename and that path would silently stop being read. It reads **`{{ .themeMode }}`, not `{{ .resolvedTheme }}`**: `theme = dark:X,light:Y` follows the OS, so `resolvedTheme` looks right and silently freezes `follow`. Windows has no template engine, so `themeMode` resolves into `__GHOSTTY_THEME__`/`__GHOSTTY_WINDOW_THEME__` in both syncs and `tstack config diff` - three copies, pinned by a test. Traps: **`off` must never be `.chezmoiremove` or a sync-side delete** (both run everywhere and would wipe a hand-written config on a box that never opted in), so `off` removes it itself, that machine only; `run_before_20-backup-ghostty.sh` takes the backup that makes `off` a *restore*; no inline comments; the Windows mirror gets blind token substitution. **Tab titles work everywhere** via `_ts_tab_title` / `Set-TsTabTitle`, and **OSC 2 only works because the `cc*` wrappers also set `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1`** - both halves are load-bearing. Full rationale, syntax-gate differences and the tmux `session_name` trap: `docs/decisions.md` §§ "Why Ghostty gets a managed config after all" / "Why Ghostty is managed on Windows too".

**Claude/Cursor voice notifications (`ccTts*`).** Opt-in TTS is configured through `tstack config tts …`; implementation lives in `bootstrap/_cc_tts.sh`, its PowerShell twins, and `bootstrap/tts-daemon`. Engines are `kokoro|chatterbox|say|auto`, and **every platform has a floor so "on" cannot mean silence** — `say` on macOS, SAPI on Windows (it *speaks*; the file path needs `ffplay`), nothing on Linux. **`ccTtsKokoroModel` is the entire mlx-audio port**: same OpenAI protocol, but the docker image answers to the literal `kokoro` and mlx-audio wants the HF repo id. pwsh defaults it at the call site (`Get-CcTtsConfig` fills top-level keys only); `?model=` reaches `/v1/audio/voices` only when set. `tstack config tts engines` (macOS) **derives** its recommendation — Docker Desktop passes no GPU to the container on Apple Silicon. Preserve these invariants: Windows/WSL hooks call `terminal-stack-tts.exe` directly; notification delivery fails open and never silently drops speech; cross-process dedupe uses `state/history.db`; mute is the `state/muted` sentinel and stops current playback; dashboard mutations require `X-TS-Token`; machine-local settings/secrets stay in `local.json` and `state/secrets.json`; and combined Windows+WSL machines save authoritative settings from WSL. Full design and failure history are in `docs/decisions.md` (TTS sections), `docs/kb/common/tts.md`, and `docs/kb/windows/tts-daemon.md`.

**agentmemory harness wiring (`bootstrap/ts-agentmemory.ps1` + `ts-agentmemory.sh`).** **The bash twin is what makes macOS and Linux capture at all** — before it those platforms served and searched but never wrote an observation, silently, because every vendor hook does `fetch(...).catch(() => {})` then `exit(0)`. `bootstrap/_agentmemory.sh` holds the edit definitions and `_merge_json_settings.sh` ports the JSONC key-splice. Exactly **two** things may differ from the `.ps1` (the secret source and the POSIX env prefix), the replace runs in **python3 reading with `newline=""`**, the **file's** line endings decide what is inserted, and the bash twin **exits non-zero in every mode** so `tstack agents` can tell a clean apply from a moved anchor — all four with their failure histories in `docs/decisions.md` § "What the bash agentmemory twin may not copy from the `.ps1`". Name it `bootstrap/ts-agentmemory.sh` exactly: `services/stacks/agentmemory/check-capture.sh` probes for that path.

**agentmemory harness wiring, shared design (`bootstrap/_agentmemory.ps1`).** Wires Claude Code, Codex and Cursor to a local agentmemory server. **Edits live once**, per agent rather than per installer — defining them per-installer is how the old Cursor script drifted into not reproducing its own installed state. **Auto-detected, no saved setting**: a host is wired when its plugin cache is present, gated on the cache rather than server reachability so the wiring survives a stopped container. Both sync paths run it (`-Check`, then `-Apply` only when something is missing), which is what makes a **plugin upgrade self-repairing** — an upgrade replaces the cache and silently reverts every edit, with nothing in any log. `tstack doctor` reports the same. **Every agent gets prompt-level retrieval**, and `AGENTMEMORY_INJECT_CONTEXT` is **inlined** into each generated hook command rather than inherited; **a 401 refreshes the secret and retries once**, wrapping `fetch` per script and failing open. The stack *reads* the secret in two places and **never writes it** — the plugin's own `.mcp.json` owns that. Never put this wiring in `docker-local`. Rationale and measurements: `docs/decisions.md` §§ "Why the agentmemory harness wiring lives here" / "Why every agent gets prompt-level retrieval".

**AgentMemory's chat model is optional and a fresh clone has none.** Storage, search and embeddings need no LLM; a model adds four things (`compression`, `summary`, `graph`, `consolidation`) and `tstack agents llm` names them either way. The states are **asymmetric**: unset is a skip every check reports, set-but-unreachable dead-letters *silently* while logging `outcome:"success"`. So all three of `OPENAI_BASE_URL`/`OPENAI_MODEL`/`OPENAI_API_KEY` ship commented — a key with no base URL falls back to `api.openai.com` while `ts-verify` still says "skip". `tstack agents llm` reads the stack `.env` so it is right while the stack is **down**, never reports a host probe as container reachability, and flags an endpoint whose `OPENAI_MODEL` is empty. It prints `host.docker.internal`, never `localhost`; `extra_hosts: …:host-gateway` is what makes that correct on native Linux.

**One memory backend (`memoryBackend`).** AgentMemory *or* Headroom's own store, never both: they do the same job, and two stores means two half-filled ones. `agentmemory` | `headroom` | `none`, **default `agentmemory`**, asked as ONE install question (`ts_prompt_memory_backend` / `Read-TsMemoryBackend`, `TS_MEMORY_BACKEND` to skip) that replaced the two independent Headroom/AgentMemory toggles - one slot makes the bad combination unrepresentable rather than merely discouraged. `agentmemoryEnabled` is **derived** from it, and `ts_memory_apply` / `Set-TsMemoryBackend` is the only writer of either; anything else writing it produces drift that `tstack doctor` reports. Headroom's memory is a compose **overlay** selected through the stack's `COMPOSE_FILE`, so Qdrant and Neo4j are never referenced or pulled unless chosen - and the overlay's `command:` is what carries **`--memory`**, which has no environment variable and is the entire feature: the base file used to set `QDRANT_URL`/`NEO4J_URI` and start both databases while the proxy never engaged memory at all (0 memories, 0 collections, 0 nodes, 900 MB of JVM, everything reporting healthy). `tstack config memory <backend>` saves and restarts headroom so the setting and the running state cannot disagree. A stack may name what it must start after in `ts-after`, and extra `--env-file` interpolation sources (never `env_file:` keys, which would hand a container someone else's secrets) in `ts-envfiles`. Rationale in `docs/decisions.md`.

**Install catalog + agent CLIs.** `bootstrap/_config.sh` holds a flat catalog (`TS_APPS_RECOMMENDED`/`OPTIONAL`) plus a **groups layer that exists only for the picker** — `shell search disk system network git editors runtimes python ai models` — so the saved `apps` array stays flat and no chezmoi `[data]` key is involved. The `ai` group (claude, codex, cursor-agent, grok, gemini, pi) **defaults to all and is still asked**; every group starts ticked and every tool stays individually untickable. **`ai` is the install ROUTE, not a category**: `ts_app_is_ai` sends its members to `ts_install_ai_cli`, which has no branch for a packaged binary — hence `llmfit` in a one-member `models` group. Two **classes** cut across the groups (`ts_apps_for_class` / `Get-TsAppsForClass`), picked by the wizard's development question; neither is a subset of the other. `ts_apps_pending` **infers** the class from the saved selection (`ts_apps_saved_class` / `Get-TsSavedAppClass`) rather than storing it, or a server is nagged forever about agent CLIs it declined. Agent CLIs never come from a package manager, so they route through `ts_install_ai_cli` / `Install-TsAiCli`, not brew/apt/winget: claude, grok and cursor-agent have native installers needing no Node; codex (npm, Node 16+) and gemini (npm, Node 20+) are gated on the Node version and *say what to do* rather than failing. **No brew fallback for gemini** — that formula is deprecated upstream. **grok's installer appends a PATH line to `~/.zshrc`**, which this stack owns whole-file, so `GROK_BIN_DIR="$HOME/.local/bin"` routes it onto the already-managed PATH instead and `dot_zshrc` carries its completions `fpath` itself. Node is managed by **fnm** (not nvm: ~10ms of shell startup vs 200-500ms), wired into both shells with `--use-on-cd`; because fnm's PATH entry is created per-shell, `ts_apps_pending` and `ts_report_installed_apps` call `ts_load_node_env` first or they would nag about npm-installed CLIs forever. The **Python group is the same shape**: `pipx`, `poetry`, `glances`, `ipython`, `httpie`, `pre-commit` have no winget package (three were carried as ids that don't resolve), so Windows routes them through `Install-TsPyTool` — `uv tool install`, else `py -m pip install --user` — after the winget pass, before the agent CLIs, in **both** `Install-TsApps` and `windows-bootstrap.ps1`'s own loop. What gets offered is `ts_app_installable` / `Test-TsAppInstallable`: *"can this platform install it"*, **not** "is it in winget" — that drift is why a Windows box missing grok/gemini/pi/cursor-agent was never told. Binary names can differ from the id (`btop` → `btop4win`); verify a new winget id with `winget show --id <id> --exact`.

**SMB shares (`tstack smb`).** `bootstrap/ts-smb.sh` and `_smb.sh` provide the macOS/Linux rclone implementation; there is deliberately no PowerShell twin. Keep shares machine-local in `shares.local.conf`, never put passwords on argv, and preserve obscured keychain storage. Never probe mount liveness with `stat`, `ls`, or globs because dead FUSE mounts can block the shell; use the kernel mount table. macOS must retain the explicit FUSE library selection and must not force the broken FSKit backend. See `docs/decisions.md` and `tstack smb doctor` for the full rationale and repair guidance.

**Update/rollback.** `tstack update` records the pre-pull HEAD to a state file (`~/.local/state/terminal-stack/rollback-sha` / `%LOCALAPPDATA%\terminal-stack\rollback-sha`) before pulling; `tstack rollback` resets the clone to it and re-applies. Both refuse on a dirty clone. The state file is only written when commits are actually incoming.

Source → destination mapping for the `windows/` subtree is **relative-path-preserving**: `windows/.wezterm.lua` → `/mnt/c/Users/<you>/.wezterm.lua`. To add a new Windows-side file, drop it at the mirror path under `windows/` — no script changes needed. Full mechanism in `docs/cross-side-chezmoi.md`.

**Username resolution.** No source file hard-codes a username. WSL/native templates use chezmoi's engine (`{{ .chezmoi.homeDir }}`); Windows-side templates under `windows/` use a literal `__WIN_USER__` token the sync substitutes. **When adding a Windows-side templated file use `__WIN_USER__`, never Go-template syntax.** Resolution order and the bootstrap that persists it: `ARCHITECTURE.md` § "Username resolution".

**User config tokens.** Windows `.tmpl` files use `__WIN_USER__` plus the saved leader, theme, tmux, mux, restore, and TTS tokens; WSL/native templates read the matching chezmoi `[data]` keys behind defaults. The Windows renderer requires Python. Keep `Read-TsChoice` and `ts_prompt_choice` behavior/output aligned, and increment `TS_WIZ_ASKED` outside command substitutions. Terminal choices remain explicit and mutually exclusive where packages conflict; WezTerm nightly is recommended, unknown/manual installs are never replaced, and the installed channel is detected rather than persisted. See `docs/decisions.md` for token mappings, theme resolution, wizard invariants, and WezTerm update logic.

**WezTerm config.** The two GUI configs (`windows/.wezterm.lua.tmpl` for Windows, `dot_wezterm.lua.tmpl` for macOS) must stay visually in sync; the pane-nav module (`windows/.wezterm/pane_nav.lua` ↔ `dot_wezterm/pane_nav.lua`, kept in sync) drives the F1–F4 direction keys (focus the pane that way, or split one there), F5/F6 PaneSelect jump/swap, Shift+F1–F4 domain splits, and the Leader+1–6 mirrors. **The tab bar is the fancy bar, fully hand-rolled** (tabline.wez was dropped — `docs/decisions.md` § "Why the tab bar is fancy and fully hand-rolled"): the retro bar's height is locked to one terminal cell and WezTerm has no multi-line bar, so `use_fancy_tab_bar = true` + `window_frame.font_size` give a taller bar, with tabs (`format-tab-title`) and status (`update-status`) drawn by our own Lua. The active tab is a solid accent block; inactive tabs with Claude panes wash with their `cc_state` tint; labels are short on purpose — the bare project leaf for Claude panes (the cc wrappers/hooks set **no `cc` prefix** any more; `strip_cc_prefix` cleans titles from not-yet-updated machines), a ` host ·` chip + directory leaf for remote panes, never a full path. The status bar is **quiet by default**: the left side renders *nothing* in the normal state (no permanent 'NORMAL' badge — a coloured badge appears only while the leader is pending or a repeat mode is live), and the right side shows the Claude fleet counts (`cc_state` across every mux pane), the non-default workspace, and a clock; Leader+s (`wezterm.GLOBAL.show_identity`) toggles the `user@host │ path` detail only. The remaining plugins — Leader+p project picker (sessionizer.wezterm) and Leader+S/L session save/restore (resurrect.wezterm) — load from **pinned forks under `github.com/martybytes`**, each `pcall`-guarded so a failed clone only loses its binding. Windows renders with OpenGL (WebGpu crashed — see `docs/decisions.md`). The mux domain (`unix_domains` + `default_domain = 'main'`) is **opt-in and off by default**, gated in both configs behind `local MUX_ENABLED` (`__WEZ_MUX__` on the Windows mirror, `{{ .weztermMux }}` on macOS) and driven by `tstack mux` (see **WezTerm mux domain** above). `.wezterm/**` is darwin-gated in `.chezmoiignore`.

**Caveat:** `chezmoi diff` shows WSL targets only, never what the `run_after` hook syncs to `/mnt/c/`. Preview Windows-side changes by applying and reading the `created`/`updated` lines.

## File-management strategies (don't mix them up)

| File | Strategy | Why |
|---|---|---|
| `~/.zshrc` | whole-file | We own every line (oh-my-zsh template + our additions) |
| `~/.claude/settings.json` (Windows) | **key-splice merge** (`bootstrap/_merge_claude_settings.ps1`) | We own only `statusLine`, `hooks`, `theme` — whatever `windows/.claude/settings.json.tmpl` renders. Claude Code writes the same file (`model`, `enabledPlugins`, `permissions`, `env`, `extraKnownMarketplaces`), so the sync splices our keys in and leaves every other byte alone |
| `~/.claude/settings.json` (WSL/macOS/Linux) | **key-splice merge** (`dot_claude/modify_settings.json.tmpl`) | Same ownership as the Windows row — `statusLine`, `hooks`, `theme`, derived from the rendered fragment, never a hard-coded list. It was a whole-file target until macOS-side Claude Code grew `agentPushNotifEnabled` and an apply started deleting it; the chezmoi `modify_` script gets the live file on stdin and returns it with only our keys replaced. An unparseable live file is echoed back untouched rather than overwritten |
| `~/.cursor/hooks.json` (Windows) | **per-entry splice** (`bootstrap/_merge_cursor_hooks.ps1`) | Everything lives under one `hooks` key and other tools use the same event arrays — agentmemory's Cursor hooks share `stop` and `postToolUse` with our TTS hooks. Ownership is per *entry* (matched on `terminal-stack` / `cursor-tts` / the `cat > /dev/null` no-op), so a key splice is not enough |
| `~/.tmux.conf`, `~/.config/starship.toml`, `~/.wezterm.lua` | whole-file **template** (`.tmpl`) | We own it; templated for leader/theme/prefix from chezmoi `[data]` (or `__TOKEN__`s on the Windows mirror). Edit the `.tmpl`, not the rendered file |
| `~/.config/git/terminal-stack.gitconfig` (both sides) | whole-file | We own it; hooked via `include.path`, user's `~/.gitconfig` stays untouched and wins |
| `$PROFILE` (Windows pwsh) | whole-file sync, **marker-block edited** | The sync copies the repo file over `$PROFILE` whole (with `.bak`); the `# ---- name-start ----` / `# ---- name-end ----` blocks organize the stack's regions. Personal content belongs in `profile.local.ps1`, never in `$PROFILE` itself |
| `~/.zshrc.local`, `profile.local.ps1`, `~/.doc.local/**` | **never managed** | Per-machine; `.zshrc.local`/`profile.local.ps1` ship `.example` twins; `~/.doc.local` is the personal `doc` layer |

**The `doc` knowledge base.** Command docs are plain `.md` files under `docs/kb/` in the clone (`common/`, `linux/`, `macos/`, `windows/`, `wezterm/`). On Windows, `scripts/sync-windows.ps1` (and the WSL `run_after` hook) also mirror `docs/kb/**` to `%LOCALAPPDATA%\terminal-stack\docs\kb\` so `doc`/`wzr` pick up updates after sync/apply; clone paths (`$TERMINAL_STACK_DIR`, workspace probes) still win for `doc edit`/`doc sync`. `docs/**` is chezmoi-ignored — canonical source stays in the clone. Per-machine/secret content lives in the untracked `~/.doc.local/` layer. `ref` and `wzr` are thin aliases into `doc`.

When modifying `$PROFILE`, edit the repo source (`windows/Documents/PowerShell/Microsoft.PowerShell_profile.ps1`) **inside an existing marker block** (`starship-stack-*`, `cli-tools-*`, `git-shortcuts-*`, …) or add a new marker block; keep `local-overrides` last. Anything a user hand-adds to the live `$PROFILE` outside the repo is replaced on the next sync (backed up, but gone from the live file) — per-machine content goes in `profile.local.ps1`. History in `docs/decisions.md` § "Why a whole-file `~/.zshrc` and a marker-block `$PROFILE`?".

## Gotchas worth remembering

These are written up at length in `docs/powershell-quirks.md`; the short version:

- **CRLF drift.** `.gitattributes` (`* text=auto eol=lf`) overrides Windows' `core.autocrlf=true` and forces LF in the working tree everywhere. Without it a Windows clone gets CRLF on checkout, which breaks `~/.zshrc` under zsh (`^M`), makes `run_after_90-sync-windows.sh` non-executable (`#!/usr/bin/env bash\r`), and produces spurious `.bak` files on every apply. Don't remove it. Rescue one file with `sed -i 's/\r$//' <file>` from inside WSL.
- **Never whole-file-copy a settings file its own app also writes.** A whole-file mirror of `~/.claude/settings.json` or `~/.cursor/hooks.json` deletes the app's own state with **no error and nothing in the diff** — that is how the agentmemory plugin got silently disabled. Both route through a merge helper on both sync paths. Add another such file and you splice it, working out whether ownership is per **key** or per **entry**. `docs/decisions.md` §§ "Why `~/.claude/settings.json` is spliced, not copied" / "…per-entry ownership" / "Why `~/.claude/settings.json` and `~/.cursor/hooks.json` are never copied".
- **JSON paths in Claude Code hooks must use forward slashes**, not backslashes. Two shell layers strip backslashes; forward slashes survive. See `windows/.claude/settings.json.tmpl` for examples (`C:/Users/__WIN_USER__/.claude/hooks/...`).
- **Tab title for `cc` wrappers uses `wezterm cli set-tab-title`, not OSC 0.** Claude Code's TUI overwrites `pane.title` (OSC) with its conversation slug; `tab.tab_title` is sticky and survives. The `format-tab-title` hook in both WezTerm configs checks `tab.tab_title` first, falling back to the active pane's cwd leaf.
- **Never auto-restart `wezterm-mux-server`.** When the mux is on, the server loads its own copy of `.wezterm.lua`, so a config change doesn't reach it — but restarting it kills every live pane. The sync scripts print a reminder instead (and only when `weztermMux` is `on`); `tstack mux restart` is the deliberate, confirmed path. Keep it that way.
- **No pwsh local may share a parameter's name, whatever the casing.** Names are case-insensitive, so a local `$foo` in a function taking `$Foo` *is* that parameter, and a typed one keeps its converter — assigning a scriptblock coerces it to a `[string[]]` of its own source text, then `& $foo` runs that text as a command. It parses cleanly, so `ParseFile` can't see it; it killed every `Read-TsMulti` call. Gated by `test_no_pwsh_local_shadows_a_typed_parameter` (AST scan of every `.ps1`); rationale in `docs/decisions.md`.
- **The exclusive-group collapse fires only for a member of the group.** `$keep` is the index just ticked; outside the group no member equals it, so all of them get cleared — ticking Ghostty silently deselected WezTerm on macOS. Both twins guard inside the helper, leaving the `-1` normalisation path unchanged.
- **`Enable-TransientPrompt` is guarded with `Get-Command`** because PSReadLine 2.4.5 doesn't export it. Don't remove the guard.
- **Never pipe `Where-Object` straight into `Set-Content`.** An empty pipeline gives `Set-Content` no value to write, so it leaves the file untouched — silently, with no error. Filtering a file down to nothing therefore *keeps* the line you meant to remove. Collect into an array and pass `-Value` (`@()` truncates as intended). A `-replace` pipeline is safe; it can't go empty.
- **`doc`'s alt-e edit binding can't hard-code fzf's `become(...)` action.** It needs fzf 0.42.0+, and on older apt fzf the unknown action makes fzf **refuse to start at all** — the whole finder, not just the key. `_doc_edit_bind` version-checks and falls back; don't revert to a bare `become(...)`. Detail in `docs/decisions.md`.

## Personal-path note

The source tree carries no hard-coded usernames. The WSL bootstrap prompts for the Windows username (default = interop-detected) and persists it under `[data].windowsUsername` in `~/.config/chezmoi/chezmoi.toml`; the sync hook substitutes it into `windows/**/*.tmpl` files at apply time, and WSL-side templates use chezmoi's native `{{ .chezmoi.homeDir }}`. If you ever see a literal username in a source file, that's a regression — replace it with `__WIN_USER__` (Windows side) or `{{ .chezmoi.homeDir }}` (WSL side, file needs `.tmpl` suffix). The `LICENSE` copyright is the one place a real name remains; update on fork if you care.
